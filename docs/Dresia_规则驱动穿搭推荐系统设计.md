# Dresia 规则驱动穿搭推荐系统设计

## 一、整体思路

如果暂时完全不接大模型，Dresia 依然可以通过规则引擎做出比较好的推荐效果。

核心不是不断增加 `if / else`，而是把推荐系统升级为：

> 用户状态理解 → 多路召回 → 穿搭组合生成 → 硬规则过滤 → 多维评分 → 去重与多样性 → Top N 推荐 → 用户反馈闭环

整体流程：

```text
用户输入 / 点击标签
        ↓
① 需求结构化
        ↓
② 用户画像
        ↓
③ 候选召回
        ↓
④ 穿搭组合生成
        ↓
⑤ 多维评分
        ↓
⑥ 去重 + 多样性排序
        ↓
      Top 3
        ↓
推荐卡片
        ↓
用户反馈
        ↓
更新用户偏好权重
```

---

# 二、第一层：用户需求结构化

不要让页面标签直接对应某个固定推荐结果，而应该把标签转换成一组推荐参数。

例如用户点击：

> 省事

不要简单写：

```js
if (tag === '省事') {
  return outfits.filter(...)
}
```

而是转换成：

```json
{
  "scene": "daily",
  "style": ["simple"],
  "operation_cost": "low",
  "item_count": {
    "max": 3
  },
  "color_complexity": "low"
}
```

也就是说：

### “省事”不是一个标签，而是一组推荐约束

例如：

```text
省事
├── 单品数量少
├── 搭配难度低
├── 颜色数量少
├── 上下装容易组合
├── 鞋子适配度高
└── 用户历史上常穿
```

这样推荐逻辑会比简单标签筛选更准确。

---

# 三、第二层：建立完整的衣服标签体系

每一件衣服不要只有名称和图片，而应该拥有丰富的结构化属性。

例如：

```json
{
  "id": "item_001",
  "category": "top",
  "sub_category": "shirt",

  "color": "white",
  "color_family": "light",

  "style": [
    "minimal",
    "commute",
    "smart"
  ],

  "scene": [
    "daily",
    "commute",
    "business"
  ],

  "formality": 3,

  "temperature": {
    "min": 18,
    "max": 28
  },

  "season": [
    "spring",
    "autumn"
  ],

  "body_effect": [
    "slim",
    "vertical"
  ],

  "matching_tags": [
    "black",
    "beige",
    "denim"
  ],

  "difficulty": 1,

  "frequency": 0.8
}
```

这些字段可以支撑：

- 天气匹配
- 场景匹配
- 风格匹配
- 颜色匹配
- 身材效果
- 用户喜好
- 搭配难度
- 季节适配
- 单品之间的兼容关系

---

# 四、第三层：多路候选召回

不要只根据一个条件召回。

例如用户：

> 明天 25°C，多云，通勤，想省事。

可以同时从多个维度召回：

```text
候选池

A：通勤衣服
B：25°C适合的衣服
C：用户常穿衣服
D：省事风格衣服
E：历史喜欢的搭配
F：最近没穿过的衣服
```

最终：

```text
A ∪ B ∪ C ∪ D ∪ E ∪ F
```

得到一个较大的候选池，例如 50 件单品，再进入组合和评分阶段。

这样会比：

```text
scene = commute
→ 找通勤衣服
→ 第一套
```

效果好很多。

---

# 五、第四层：核心推荐对象应该是 Outfit

Dresia 页面展示的不是单件衣服，而是一整套穿搭：

```text
上装
+
下装
+
鞋子
+
外套
```

因此核心推荐对象应该是：

> Outfit（穿搭组合）

例如：

```json
{
  "outfit_id": "outfit_001",

  "items": [
    "white_shirt",
    "black_trousers",
    "loafer"
  ],

  "style": "minimal",
  "scene": "commute"
}
```

系统应该有一个：

> Outfit Combination Generator（穿搭组合生成器）

例如：

```text
上装 10 件
×
下装 10 件
×
鞋子 8 双
×
外套 5 件
```

理论上会产生大量组合。

因此必须先通过硬规则过滤，再评分。

---

# 六、硬规则 + 软规则

这是规则引擎设计的核心。

## 6.1 硬规则

违反就直接淘汰。

例如：

```text
❌ 温度 28°C + 厚羽绒服

❌ 正式商务会议 + 拖鞋

❌ 用户明确不喜欢裙子 + 半身裙

❌ 用户没有这件衣服 + 虚构商品
```

代码层面可以直接：

```js
return false
```

---

## 6.2 软规则

不直接淘汰，而是扣分。

例如：

```text
颜色不太协调
→ -10

风格匹配一般
→ -8

用户以前很少穿
→ -5

搭配比较复杂
→ -5
```

最终形成：

```text
硬规则 → Filter

软规则 → Score
```

这比所有逻辑都写成 if / else 更灵活。

---

# 七、建立多维推荐评分模型

例如可以先采用：

```text
总分 =
天气匹配       × 25%
+ 场景匹配       × 20%
+ 风格匹配       × 15%
+ 用户偏好       × 15%
+ 颜色协调       × 10%
+ 搭配完整度     × 5%
+ 新鲜度         × 5%
+ 搭配难度       × 5%
```

例如一套搭配：

| 维度 | 分数 |
|---|---:|
| 天气 | 95 |
| 场景 | 90 |
| 风格 | 88 |
| 用户偏好 | 80 |
| 颜色 | 92 |
| 完整度 | 100 |
| 新鲜度 | 60 |
| 难度 | 90 |

最终：

```text
Score =

95 × 0.25
+ 90 × 0.20
+ 88 × 0.15
+ 80 × 0.15
+ 92 × 0.10
+ 100 × 0.05
+ 60 × 0.05
+ 90 × 0.05

≈ 89.5
```

---

# 八、增加“多样性”，避免推荐千篇一律

如果每次都简单：

```text
Score DESC
```

那么用户每次打开 Dresia 都可能看到同几套衣服。

例如：

```text
第1套：白衬衫 + 黑裤
第2套：白衬衫 + 黑裤
第3套：白衬衫 + 黑裤
```

即使评分很高，体验也不好。

因此需要加入：

> Diversity（多样性）

例如：

```text
最终分数 =
推荐匹配分 × 80%
+
多样性分 × 20%
```

还可以限制：

> Top N 推荐之间至少存在 1～2 个核心单品差异。

最终可以形成：

```text
① 通勤利落
② 轻松自然
③ 精致低调
```

而不是三套几乎一样的搭配。

---

# 九、推荐去重机制

例如第一套：

```text
白衬衫
黑西裤
乐福鞋
```

第二套不能只是：

```text
白衬衫
黑西裤
小白鞋
```

可以增加：

```text
至少 1～2 个核心单品不同
```

或者直接控制：

```text
Top 1 → 偏正式
Top 2 → 偏休闲
Top 3 → 偏时髦
```

这样用户会明显感觉推荐更丰富。

---

# 十、给每种用户需求定义“推荐策略”

这是非常适合 Dresia 的设计。

例如用户选择：

> 省事

推荐策略：

```json
{
  "strategy": "easy",
  "weights": {
    "matching": 0.4,
    "simplicity": 0.3,
    "preference": 0.2,
    "novelty": 0.1
  }
}
```

用户选择：

> 元气

```json
{
  "strategy": "energetic",
  "weights": {
    "style": 0.35,
    "color": 0.25,
    "matching": 0.2,
    "preference": 0.1,
    "novelty": 0.1
  }
}
```

用户选择：

> 显瘦

```json
{
  "strategy": "slim",
  "weights": {
    "body_effect": 0.4,
    "proportion": 0.25,
    "style": 0.15,
    "preference": 0.1,
    "color": 0.1
  }
}
```

这样同一个衣柜，因为推荐策略不同，可以得到完全不同的推荐结果。

# 十一、最重要：建立用户反馈闭环

即使没有 AI，也可以通过用户行为让推荐越来越准确。

记录：

```text
点击推荐
查看详情
收藏
穿过
喜欢
不喜欢
换一套
点击某件衣服
```

例如用户连续一段时间表现出：

```text
喜欢：
米色
白色
黑色

喜欢：
直筒裤
衬衫
针织

不喜欢：
碎花
高饱和色
裙装
```

可以动态更新偏好权重：

```text
white      +5
beige      +4
black      +3

shirt      +4
trousers   +5

floral     -5
dress      -3
```

最终形成：

```json
{
  "user_preference": {
    "colors": {
      "white": 0.85,
      "beige": 0.78,
      "black": 0.72
    },

    "items": {
      "shirt": 0.86,
      "trousers": 0.81,
      "dress": 0.25
    },

    "styles": {
      "minimal": 0.88,
      "casual": 0.72,
      "sweet": 0.31
    }
  }
}
```

这就是一个轻量级的个性化推荐系统。

# 十二、让“对话”实际上改变推荐规则

即使没有大模型，也可以让用户感觉系统在理解对话。

例如用户：

> 我想穿得简单一点

转换：

```text
style = minimal
complexity = low
```

推荐：

> 给你挑了 3 套简单好搭的。

用户继续：

> 第一套不错，但今天想穿得更有精神一点。

系统调整：

```text
原：

minimal = 0.8
complexity = low

↓

new：

minimal = 0.7
energetic = 0.6
```

然后重新计算推荐。

所以：

> 用户觉得“它听懂了我的话”。

实际上背后可以是：

```text
关键词
↓
参数
↓
权重变化
↓
重新排序
```

完全不需要大模型。

# 十三、没有大模型，也可以支持一定程度的自然语言

可以先使用：

> 关键词 + 同义词 + 意图规则

例如：

```json
{
  "easy": [
    "简单",
    "省事",
    "不想花时间",
    "懒得搭",
    "好搭"
  ],

  "formal": [
    "正式",
    "商务",
    "开会",
    "见客户"
  ],

  "slim": [
    "显瘦",
    "显得瘦",
    "不要显胖"
  ]
}
```

用户输入：

> “明天开会，想正式一点，但不要太严肃。”

可以解析成：

```json
{
  "scene": "business",
  "formality": "medium_high",
  "style": "minimal",
  "avoid": ["too_formal"]
}
```

再交给规则引擎进行推荐。

# 十五、针对你现在的 Dresia 页面，建议优先改这 5 个地方

## 1. 顶部标签变成“推荐策略”

现在：

```text
省事 | 元气 | 低调 | 显瘦
```

可以保留。

但点击以后不是简单筛选，而是：

```text
省事
↓
改变推荐权重
↓
重新计算
```

---

## 2. 增加对话输入

例如：

```text
┌─────────────────────────────┐
│ 今天要去见客户，但不想穿得太正式 │
└─────────────────────────────┘
```

系统解析：

```text
场景：商务
正式度：中
风格：简约
需求：不要太严肃
```

---

## 3. 推荐卡片告诉用户“为什么”

不要只有：

> 通勤套装

可以显示：

```text
25°C · 多云
通勤
偏正式
省事
```

甚至：

> 你最近比较常穿浅色上衣，所以这次优先给你推荐了浅色搭配。

这样会明显增加推荐的可信度。

---

## 4. “换一套”不能随机

不要：

```js
Math.random()
```

应该：

```text
当前推荐
↓
排除已经看过
↓
保留用户条件
↓
降低当前组合相似度
↓
重新排序
↓
下一套
```

这样用户点击“换一套”时，推荐才会真正发生变化。

---

## 5. 规则一定要配置化

不要把所有规则写死在代码里。

例如：

```json
{
  "strategy": "easy",

  "weights": {
    "weather": 25,
    "scene": 20,
    "style": 15,
    "preference": 15,
    "color": 10,
    "novelty": 5,
    "difficulty": 10
  },

  "constraints": {
    "max_items": 4,
    "max_colors": 3,
    "temperature_tolerance": 3
  }
}
```

这样产品经理调整：

> “省事权重太低了。”

只需要改配置，不需要修改核心代码。

# 十七、最终目标

如果暂时完全不接大模型，我建议 Dresia 的核心能力定义成：

> **标签/关键词 → 用户意图 → 多路召回 → 穿搭组合 → 硬规则过滤 → 权重评分 → 多样性排序 → 用户反馈学习**

而不是：

> **一堆 if / else → 推荐衣服**

前者已经是一个比较正规的**推荐系统 MVP**。

而且以后接入大模型时，大模型主要负责：

```text
自然语言
   ↓
Intent JSON
```

后面的：

```text
召回
↓
规则
↓
评分
↓
排序
↓
推荐
```

都可以继续保留，不需要推倒重来。
